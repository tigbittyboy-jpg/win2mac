# Integrated overhaul — 0.2 preview

## Delivered

- Native Home, Library, Compatibility and Settings navigation. Home file selection and file-URL drop share the same passive import path. Search, grid/list, sorting, favorites, rename, custom icons, per-app settings, folders/logs and launch history persist locally. Appearance/display/sort preferences use UserDefaults; application metadata stays in atomic JSON.
- Bounded native PE inspection describes PE32/PE32+, x86/x64/ARM64/ARM64EC, unknown CPUs, CLR presence/32-bit requirement, and imports. Checks reject truncated headers, out-of-file sections and invalid directory mappings. Installer candidates use MSI imports or known embedded installer signatures; filenames alone do not establish an installer. Users can explicitly mark an ambiguous installer.
- Capability routing chooses among declared, accessible generic Wine engines and checks host/Rosetta prerequisites. New apps receive a separate environment automatically after informed approval. Existing associated environments retain their graphics/arguments. Native/universal engines are preferred only after Windows capability declarations; an ARM64 frontend does not confer ARM64 Windows support.
- Prefix initialization waits up to 30 seconds after a successful wineboot for actual drive_c/system.reg readiness. Approval-gated owned-prefix repair performs at most one wineboot update and verifies structure without changing existing WINEARCH or deleting data. Inherited WINEARCH/WINEPREFIX values are removed before Bridge-controlled settings are applied, preserving other provider environment values. Each repair attempt and outcome is recorded. Foreign and win32 prefixes, active leases and imported DXVK transactions block unsafe repair. Recoverable partial prefixes keep their ownership identity.
- Complete streamed launch/probe/preparation output is written to private local log files; the UI console remains bounded and optional. Evidence-based diagnostics distinguish graphics/dependencies/permissions/architecture/prefix/crash failures. Exit 3 alone stays an unexplained application failure. Exit 0 is displayed as a process result, never certified game compatibility.
- Configured apps can remember explicit execution approval. SHA-256 binds consent to the selected EXE and engine bytes, paths, working directory, arguments, environment overrides, graphics setting and declared host/guest capabilities. Changes require new approval. Hashing runs off the UI actor. External engine dependencies are not all hash-pinned; this does not make software safe or remove filesystem races. First-time execution/preparation, probes, repairs and library imports retain separate consent.
- Installer completion offers a bounded, read-only target scan in conventional installation folders. Symlinks are not followed, Windows system executables are excluded, ambiguous targets require user selection. The installer remains labeled as an installer.
- Existing static-core signing, DXVK backups/restoration, runtime-default/Vulkan graphics choices, ownership-controlled deletion and old library associations remain in place.

## Explicit boundaries and remaining work

This is a substantial integrated preview, not universal compatibility or a replacement for Wine. Backend execution supports generic provider-configured Wine commands. CrossOver and GPT paths are identified as requiring dedicated adapters and fail closed; Bridge does not assume their command, graphics or license models. ARM64/ARM64EC Windows files can be inspected but cannot be executed by these adapters. CLR detection is descriptive; it does not install .NET or determine every AnyCPU/JIT behavior.

Automatic repairs cover launcher-owned environment initialization only. No repeated game restarts, random DLL downloads, Microsoft runtime redistribution, registry guessing, security bypasses or automatic Rosetta installation occur. Other failures provide evidence and next steps. Structural repair is not proof that a game works. A prefix is not a security sandbox.

Icons use macOS file icons where available plus user-selected images; native extraction of every Windows PE icon/name resource is not implemented. Installer scans cannot identify targets outside conventional folders or distinguish every launcher/uninstaller. Selection remains explicit. Customization notifications/playtime tracking and a curated compatibility profile database are not implemented. Removing a library entry leaves its files, logs and environment intact.

Logs are local, unredacted and can contain private application output; diagnostic export redacts known paths heuristically. No automatic disk retention policy is applied to avoid silently discarding troubleshooting history. Users manage Logs in Settings. Process lifetime tracks Wine's immediate child; detached games may outlive it. External Wine processes and separate Bridge instances are not covered by the in-process lease mechanism.

## Validation boundaries

Linux executes the backend XCTest suite with synthetic PE/Mach-O fixtures and mocked Wine behavior, plus trusted system-process pipe checks. Hosted macOS CI compiles SwiftUI against the SDK, runs additional actual-model XCTest cases and checks extracted signed-app window/library startup. These checks do not run a Windows game or verify FPS, font rendering, Rosetta translation or an actual Wine installation. Manual UI interaction, keyboard/accessibility and graphics require an Apple Silicon Mac. Publication and CI outcomes are recorded in VALIDATION.md after verification.
