# Win2Mac compatibility rebuild audit

Audit baseline: `9daa5019ac746732d588a7d8fe12b18a86bc9cff`, 14 October 2026. Inspected the SwiftPM graph, all core services and app/model entry points, generated Xcode project and generator, test coverage, development/release scripts, CI, and existing architecture/validation records before refactoring. Baseline Linux XCTest: 51 tests passed. Historical macOS release results belong to their recorded commits, not this rebuild.

## Working components to preserve

The native SwiftUI frontend delegates through injectable Sendable services. Bounded passive PE parsing separates machine type and container format and reports CLR/import evidence. Swift 6 concurrency, explicit executable/argument Process calls, concurrent pipe draining, cancellation/timeouts, complete private streamed logs, and bounded console/result capture already work. Runtime discovery is passive; launch, version probing, prefix initialization and repair are approval gated. x86 needs a separately declared provider WoW64 capability; ARM Windows execution is refused. Prefix readiness waits for actual files. JSON writes are atomic and refuse corrupt/future stores. Existing library IDs and game settings survive additive metadata. DXVK has captured-source approval, original DLL backups, a transaction journal, installation checks and reversible graphics settings. Retain static core linkage and hardened runtime.

## Confirmed architectural gaps

1. Runtime identity is a mutable path plus user declarations. Version probes do not pin even the primary binary; provider family is inferred from path substrings. An engine update can silently change the runtime behind an existing prefix. There is no explicit provenance/revision record or rollback selection policy. Discovering a newer runtime must not replace an existing association.
2. Child processes inherit graphics and loader variables other than WINEARCH/WINEPREFIX. Runtime Default can consequently inherit a parent WINEDLLOVERRIDES or WINE_D3D_CONFIG, defeating the displayed selection. A centralized environment policy must make the planned and executed settings agree while retaining ordinary provider configuration.
3. Graphics is stored on a bottle. Multiple apps can reference one bottle, and the current app-settings picker changes that shared bottle. Per-game overrides need explicit effective configuration; native DLL changes are prefix-wide and cannot be described as per-game. Incompatible overrides must be refused before execution.
4. Steam and dependency services are absent. The installed-target scan cannot parse Steam manifests or launch through Steam authentication. PE imports are evidence of requested DLLs, not proof of a missing redistributable. Install attempts need reviewed artifacts, per-prefix leases, persistent pending/failure/success records, and post-install evidence; exit zero alone is insufficient.
5. Prefix repair is a single wineboot update, not a backup or rollback system. Atomic library saving does not make multi-file prefix changes atomic. There are no environment snapshots, duplication or data-preserving reset controls. Cross-process/external Wine writes remain outside in-memory leases.
6. LaunchDiagnosis uses broad substrings in combined output and has no confidence/evidence fields. Steam authentication, anti-cheat and DRM should only be suggested from specific errors; incidental mentions must not be treated as verified blockers. The saved failure text is generic and loses the structured reason.
7. There is no compatibility matrix separating execution results from human-verified rendering/input/audio/stability. Zero exit and a version response cannot prove playable status. CPU/RAM/OS can be measured locally, but FPS and Metal/game functionality cannot be invented.
8. UI navigation has no Steam, Applications or Diagnostics destinations. BridgeModel coordinates persistence and operations, but new business policies belong in core services, not SwiftUI handlers. Branding remains Bridge; preserve the legacy data path to avoid an apparent data reset when displaying Win2Mac.

## Duplication and hardcoded assumptions

ExecutableValidator correctly wraps the parser for existing call sites; retain it rather than introduce a second parser. Prefix paths and ownership checks are centralized, but UI approval/fingerprinting and execution independently build graphics environments. Centralize launch planning. Generic Wine currently assumes win64 prefixes and `wine wineboot -u`; these are supported adapter constraints, not universal runtime capabilities. CrossOver/GPT need provider adapters and remain unavailable instead of using private binaries. Rosetta is checked by a runtime file's presence, which is a prerequisite hint rather than proof of successful Intel execution. Runtime-default and opt-in Vulkan are requests, not hardware support certificates.

## Failure evidence

Existing validation documents report Isaac exit 3 after OpenGL/window activity; no actual executable or complete reproducible hardware case is supplied. This is an unresolved failure, not confirmed Visual C++, CPU or DirectX failure. CARL was reported to launch, but its binary/runtime/rendering matrix is unavailable. Preserve its associations and imported graphics. Do not replace the engine or change its prefix to pursue unproven fixes.

## Implementation boundaries

Rebuild missing policies around retained services: explicit runtime identity; one launch/environment policy; per-app requested configuration; approved local prerequisite installers with verified outcomes; managed Steam import/scanning/launch; offline environment backup/duplication/restore with retained old data; structured diagnostics; evidence-based test matrix; native UI integrations. Existing libraries remain readable. No engine, game, commercial graphics library or random DLL will be bundled. Runtime/provider distribution selection and real Windows compatibility require current provider terms plus Apple Silicon testing. Linux can execute backend regression/process tests, not AppKit, Wine, Steam authentication, Metal, macOS crash reporting or rendering. Every unsupported integration remains visible.
